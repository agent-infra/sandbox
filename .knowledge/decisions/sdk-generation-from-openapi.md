# SDK Generation from OpenAPI

## Context

Two first-party SDKs (Python, JavaScript) plus a Go SDK must stay consistent
with a 123-path / 255-schema HTTP API. Hand-writing and hand-maintaining
them would guarantee drift.

## Current decision

All SDKs are **generated by Fern** from a single OpenAPI 3.1 spec stored in
this repo at `website/docs/public/v1/openapi.json`. Configuration lives in
`sdk/fern/generators.yml`:

- `python-sdk` group → `fernapi/fern-python-sdk` → output
  `sdk/python/agent_sandbox` (package `agent_sandbox`, pydantic validation
  on, smart unions, root client class `Sandbox`).
- `js-sdk` group → `fernapi/fern-typescript-sdk` → output `sdk/js/src`
  (noSerdeLayer, neverThrowErrors, custom fetcher allowed, namespace
  `Sandbox`).
- `sdk-go` group → `fernapi/fern-go-sdk` → output points **outside the
  repo** (`../../sandbox-sdk-go`); `sdk/go/` here is only a pointer README.

The spec embeds Fern extensions (`x-fern-sdk-group-name`,
`x-fern-sdk-method-name`), so SDK naming/namespace decisions are made in
the spec, not in generator config.

### Hand-written layers kept separate from generated code

- **JS**: `sdk/js/src/providers/**` (BaseProvider + VolcengineProvider with
  request signing) and the test suite under `sdk/js/__test__/` are
  hand-maintained. There is a `fern-customizations.test.ts` confirming
  post-generation customizations are regression-tested.
- **Python**: `sdk/python/setup.py`, `publish.sh`, packaging metadata.
- Generated files carry "This file was auto-generated by Fern" headers and
  must not be hand-edited.

## Evidence

- `sdk/fern/generators.yml` (all three generator groups and configs).
- `sdk/python/agent_sandbox/client.py`, `sdk/js/src/Client.ts`,
  `sdk/js/src/BaseClient.ts` — all Fern-generated headers.
- CI (`sdk-ci.yml`) triggers on changes to `sdk/js/**` and `sdk/fern/**`,
  acknowledging the spec → SDK coupling.

## Consequences

- The canonical edit flow for API surface changes is: update the spec (which
  in practice means re-exporting from the running FastAPI service — the spec
  is a generated artifact itself) → run Fern → commit regenerated SDKs →
  adjust hand-written layers/tests.
- Because the spec is an *export* of the runtime service, spec updates are
  gated on runtime releases (observed drift: spec 1.9.4 vs image 1.11.0).
- Dual-publishing (PyPI + npm) is orchestrated by `sdk-publish.yml`, which
  bumps versions, publishes, and commits the bumped version files back.
- The Python SDK bundles `volcengine-python-sdk` as a hard runtime
  dependency to support the provider layer.
